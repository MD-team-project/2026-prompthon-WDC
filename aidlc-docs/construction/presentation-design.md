## 1. 모범 예시에서 가져온 것

`AgentWorker_보고_공유용_v1_1_5.html`은 32장이지만 **본문은 7장**이고 나머지 25장이
Appendix다. 그 7장의 골격을 그대로 쓴다.

| 기준 덱 | 역할 | 우리 덱 |
|---|---|---|
| 표지 | 번호 없음 | 표지 |
| **SECTION 01** Intro | Hook. 서술형 문단 + **어젠다 선언**으로 마무리 | SECTION 01 Intro |
| **SECTION 02** Enterprise AaaW Journey | 전개·여정. 가장 큰 다이어그램 | SECTION 02 전환의 방향 |
| **SECTION 03** Agent Worker | 핵심 개념 정의 | SECTION 03 차별점 |
| **SECTION 04** 업무 시나리오 | 실제 사례 카드 그리드 | SECTION 04 기술과 검증 |
| **SECTION 05** Outro | 정리 | SECTION 05 Outro |
| 감사합니다 | 번호 없음 | 감사합니다 |

### 차용한 구조적 장치

1. **`SECTION 01`~`05` 번호는 본문 5장에만.** 표지와 감사합니다는 번호 없음. 심사위원이
   지금 몇 번째 이야기를 듣는지 항상 알 수 있다
2. **`.section-header`** = `.section-label`(SECTION 0N) + `.section-title` +
   `.section-title-bar`. `page-patterns.md`의 `.kicker` 대신 **기준 덱의 이 조합을 쓴다**
3. **Intro는 서술형 문단**(`.intro-narrative` > `.intro-body` 여러 개)으로, 마지막에
   **"오늘 이 세 가지를 말씀드립니다"** 식 어젠다 선언으로 닫는다. 기준 덱의
   `.intro-turn`에 해당하는 장치
4. **Outro와 감사합니다를 분리한다.** 기준 덱이 그렇게 하고, 이유가 있다 — Outro는
   내용의 정리이고 감사합니다는 발표의 종료다. 우리는 그 사이에 **시연**이 들어간다
5. **사례에는 출처 칩**을 붙인다 (기준 덱: `KB손해보험 사례`, `Optapex 사례`).
   우리는 검증 항목에 근거 파일명을 칩으로 붙인다

### 의도적으로 버린 것

| 기준 덱 요소 | 왜 버리는가 |
|---|---|
| **Appendix 25장** | 사용자 지시로 제외. 5분 발표에 별첨을 넘길 시간이 없다 |
| `intro-jump-btn` / "상세 →" 점프 버튼 | 점프할 Appendix가 없다. 링크 없는 버튼은 혼란만 준다 |
| 시나리오 카드 → 상세 슬라이드 점프 | 같은 이유. SECTION 04는 자립적이어야 한다 |
| **Intro의 텍스트 밀도** | 기준 덱 Intro는 사실상 대본이 화면에 있다. 그건 *공유용* 문서를 겸하기 때문이고, 우리는 심사위원이 **나를 보는** 5분이다. 구조는 쓰고 분량은 절반으로 |

마지막 항목이 가장 중요한 판단이다. 기준 덱은 발표 후 읽히는 문서를 겸하므로 화면에
문장이 많아도 손해가 아니다. 우리 덱은 읽히지 않고 **발표되기만** 하므로, 화면의 문장이
많으면 내 목소리와 경쟁한다.

**초과 시 자를 순서**: SECTION 03의 사업성 한 줄 → SECTION 04의 검증 칩 1개 →
SECTION 01의 페르소나 카드 1개. **장을 통째로 지우지 않는다** — 7장 각각이 배점 항목
또는 프레임을 담당한다.

**Slide 6(감사합니다)은 시연 후 복귀 화면**으로도 쓴다. SECTION 05에서 시연으로 나가고,
시연이 끝나면 6번으로 돌아와 핵심 메시지를 한 번 더 말하고 끝낸다.

> **사용자가 자기도 모르게 정착한 패턴에, 캐릭터가 처음으로 이름을 붙인다.**

표지 pretitle, SECTION 03 Hero, 감사합니다에 **세 번** 등장한다.

**이 문장을 고른 이유**: 심사위원이 반드시 물을 질문이 "그거 그냥 프리셋 추천 아니냐"

(`setRollerZone`/`setIntensity`/`setDuration`)뿐이고 '비 오는 날 모드'라는 프리셋이
애초에 존재하지 않는다는 것.

### Slide 1 — SECTION 01 · Intro (45초, 배점 25)

기준 덱 Intro의 **서술형 + 어젠다 선언** 구조를 쓰되 분량은 절반.

- **`.section-header`**: `SECTION 01` / `Intro`
- **`.intro-body` 3문단** — 말하듯 쓰되 한 문단 2줄 이내:
  1. LG 제품에는 이미 쓸 만한 기능이 많습니다. 문제는 그걸 **찾아서 설정해야 한다는 것**
     입니다.
  2. ThinQ는 버튼과 슬라이더의 격자입니다. 기능이 늘어날수록 화면이 깊어지고,
     **아무것도 학습하지 않습니다.**
  3. 제품은 사용 기록을 이미 갖고 있습니다. 그런데 그걸로 아무것도 하지 않습니다.
- **`.intro-turn`** (기준 덱의 `.intro-dir-turn` 대응) — 어젠다 선언:
  > **하나,** 설정 화면을 없애고 **캐릭터가 제품의 UI**가 되는 구조.
  > **둘,** 그 위에서 스스로 스킬을 발견하는 **자율 발견**.
- **하단 페르소나 칩 2개** (`personas.md`): `Min-seo — 기능을 못 찾아 기본값만 쓴다` /

페르소나를 카드가 아니라 **칩**으로 내린 것은 의도적이다. 25점 항목이지만 심사위원이
이미 동의하는 내용이라 길게 설명할 이유가 없고, 어젠다 선언이 이 장의 주인공이어야 한다.

### Slide 3 — SECTION 03 · 프리셋 추천이 아니다 (70초, 배점 25) — 덱의 중심

기준 덱의 "Agent Worker" 개념 정의 자리. **5분 전체에서 가장 중요한 장.**

- **`.section-header`**: `SECTION 03` / `프리셋 추천이 아니다`
- **Hero 문구(대형)**: `사용자가 자기도 모르게 정착한 패턴에, 캐릭터가 처음으로 이름을 붙인다`
- **좌우 대조 2단** — 이 장의 시각적 중심:

| 좌: 프리셋 추천 | 우: 자율 발견 |
|---|---|
| 메뉴에 이미 있는 항목을 고른다 | 메뉴에 **없던 조합**을 만든다 |
| 사람이 후보를 정의한다 | 승인 게이트가 없다 |
| "자주 쓰신 모드입니다" | "비 오는 날엔 허리를 강하게 쓰시네요" |

- **골드 카드 — 반박 차단 1줄**: 기기가 노출하는 어휘는 롤러 위치·강도·시간 같은
  **원시 설정값**뿐이고, '비 오는 날 모드'라는 프리셋은 존재하지 않는다
- **회색 1줄 — 사업성**: 이번 빌드에서 제품 2종을 추가할 때 바뀐 것은 툴 정의와
  픽스처였고 구조는 그대로였다. **제품 추가는 아키텍처가 아니라 데이터다**

사업성을 **이미 일어난 사실**로 말한다. "확장 가능합니다"보다 강하고 한 줄이면 된다.
사업성은 심사위원이 보는 5가지에는 있으나 배점 4항목에는 없으므로 전용 장을 주지 않는다.

### Slide 4 — SECTION 04 · 발견은 요청 경로 밖에서 (70초, 배점 25)

기준 덱의 시나리오 카드 그리드 자리. 우리는 **아키텍처 + 검증**으로 쓴다. 실제 시나리오는
바로 다음의 라이브 시연이 담당하므로 여기서 재연하지 않는다.

**934px 오버플로 1순위 감시 대상.**

- **`.section-header`**: `SECTION 04` / `발견은 요청 경로 밖에서 일어난다`
- **좌→우 흐름도**:
  ```
  사용자 → [제어 에이전트 · Bedrock] → device API → 기기 상태
                                            ↓ 사용 이벤트 누적
                              [Skill Discovery · EXAONE] ← 앱 컨텍스트
                                            ↓
                                      발견된 스킬 → 캐릭터가 먼저 알림
  ```
- **골드 강조 2곳만**: EXAONE 노드, 그리고 요청 경로와 발견 경로를 가르는 점선
- **설계 칩 3개**:
  1. **EXAONE**(Friendli dedicated)이 발견과 민감 데이터 접근, **Bedrock**이 제어
  2. 발견은 **비동기**. 사용자 상호작용을 절대 막지 않는다
  3. 앱 컨텍스트 원본은 **EXAONE만** 본다. 제어 에이전트는 완성된 문장만 받는다
- **검증 칩 3개** — 기준 덱이 사례에 출처 칩을 붙이듯 근거 파일을 칩으로 붙인다:
  1. Friendli **dedicated** 엔드포인트 tool calling `verification-results.md`
  2. 실제 배포된 **DynamoDB까지 end-to-end** `api-examples.md`
  3. **패턴이 없으면 없다고 답한다** — 비패턴 데이터 2회 확인 `discovery-review.md`

**검증 칩 3번을 골드로 강조한다.** "항상 뭔가를 찾아내는 에이전트는 발견하는 게 아니라
만들어내는 것"이라는 한 줄을 붙인다. 절제를 보여주는 것이 성공 사례보다 신뢰를 준다.

설계 칩 3번은 프라이버시 아키텍처 주장이고 구현으로 뒷받침된다
(`FR-5.11`, `discovery/relevance.ts`). 슬로건이 아니라는 점이 이 장의 가치다.

**EXAONE 필수 확인 항목은 여기서 소화된다.** 배점이 없으므로 전용 장을 주지 않는다.

**오버플로 대비**: 칩 6개 + 흐름도가 한 장에 들어간다. 넘치면 설계 칩 2번을 빼고
흐름도의 점선 라벨로 대체한다 — 다이어그램이 이미 그 내용을 말한다.

### Slide 5 — SECTION 05 · Outro (20초)

기준 덱의 Outro 자리. 정리 + 시연으로 나가는 문.

- **`.section-header`**: `SECTION 05` / `Outro`
- **정리 1줄**: 설정 화면을 없애고, 캐릭터가 제품을 배웁니다.
- **`step` 카드 3개** — 시연 3비트와 1:1 대응:
  1. 자연어로 제어한다 — 설정 화면 없이
  2. 캐릭터가 **먼저 말을 건다** — 아무도 요청하지 않은 스킬을 발견해서
  3. 심사위원이 한 문장으로 고친다 — 눈앞에서 바뀐다
- **우측에 FE 캐릭터 화면 스크린샷.** 덱에서 실제 UI가 나오는 유일한 장이고 바로 다음이
  실물 시연이라 연결이 자연스럽다

**이 장을 띄운 상태로 시연을 시작한다.** 심사위원이 무엇을 볼지 알고 보는 것과 모르고
보는 것의 차이가 크고, 특히 Beat 2의 "기다림"이 설계된 것으로 읽힌다.
